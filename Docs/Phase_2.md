# Phase 2: User Login & JWT Authentication

This phase implemented the secure user login functionality, generating a JSON Web Token (JWT) on successful authentication to enable stateless, session-less user authorization.

## 📝 Detailed File Breakdown

### 1. `backend/src/services/authService.js` (Modified)
*   **Purpose**: Manages business logic verification for logging in users.
*   **Key Responsibilities**:
    *   Finds a user by their email in MongoDB. Since the `password` field is hidden by default (`select: false`), the service explicitly queries it using `.select('+password')`.
    *   Compares the plain-text password from the request with the database hash using the `comparePassword()` helper.
    *   Generates a cryptographically signed JWT containing user identity (`id`) and privileges (`role`).
    *   Sanitizes and returns the final user document (deleting the password) alongside the token.

### 2. `backend/src/controllers/authController.js` (Modified)
*   **Purpose**: Handles login HTTP requests.
*   **Key Responsibilities**:
    *   Extracts `email` and `password` parameters from the request body.
    *   Performs basic payload presence validation (returns `400 Bad Request` if either is missing).
    *   Invokes `authService.loginUser`.
    *   Sends a `200 OK` response with the token and user details, or passes service errors to the global error middleware via `next(error)`.

### 3. `backend/src/routes/authRoutes.js` (Modified)
*   **Purpose**: Maps endpoints to controllers.
*   **Key Responsibilities**:
    *   Declares the endpoint `POST /login` and links it to `authController.login`.
    *   Exposes the authentication endpoint externally at `POST /api/auth/login`.

## 💡 Interview Highlights (Core Concepts)

Here are the key technical concepts and security decisions to highlight in an interview:

### 🔑 1. Password Comparison Flow & Mongoose `select: false`
*   **The Problem**: In our `User` model, the `password` field has `select: false`. Under normal Mongoose queries (e.g., `User.findOne({ email })`), MongoDB excludes the password field from the query result to prevent accidental leakage (e.g., when returning user profiles).
*   **The Solution**: During login, we must verify the password. We use `User.findOne({ email }).select('+password')` to force MongoDB to return the password hash.
*   **Hash Comparison**: We then run `bcrypt.compare(enteredPassword, hashedPassword)` via the schema method. Because bcrypt salts and hashes passwords, we cannot compare them in plain text.

### 🪙 2. JWT (JSON Web Token) Structure & Generation
*   **Concept**: JWT is a stateless session token. Once generated, the server does not need to store it in a database to authenticate requests.
*   **Structure**: Composed of three parts separated by dots (`.`):
    1.  **Header**: Specifies the hashing algorithm (e.g., HS256) and token type (JWT).
    2.  **Payload**: Holds user claims (we store `id` and `role`). **Important**: The payload is base64-encoded, not encrypted. Do not store sensitive details like passwords here.
    3.  **Signature**: Generated by combining the encoded header, encoded payload, and a secret key (`JWT_SECRET`) using the algorithm specified in the header. This ensures the token cannot be tampered with.
*   **Implementation**: Signed via `jwt.sign()` with an expiration limit (`expiresIn: '1d'`).

### 🛡️ 3. Security Considerations
*   **User Enumeration Protection**: The service returns a generic message (`"Invalid email or password"`) for both a non-existent email and an incorrect password. This prevents attackers from guessing valid email addresses.
*   **Timing Attack Mitigation**: Bcrypt uses constant-time algorithms for comparison to defend against timing-based analysis attacks.
*   **Output Sanitization**: The password is delete-copied out of the returned object (`delete sanitizedUser.password`), ensuring that hash representations are never exposed over the network.

## 🧪 Testing Guide

Follow these steps to run and test the registration and login flows.

### 🏃 Step 1: Start the Backend Server
Make sure MongoDB is running, then start the server in your terminal:
```bash
cd backend
npm run dev
```

### 📡 Step 2: Register a New User
If you haven't registered a user yet, run this `curl` command (or use Postman):

```bash
curl -X POST http://localhost:5000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"name": "Interview Candidate", "email": "candidate@example.com", "password": "securepassword123", "role": "candidate"}'
```

**Expected Response (`201 Created`):**
```json
{
  "success": true,
  "message": "User registered successfully",
  "data": {
    "name": "Interview Candidate",
    "email": "candidate@example.com",
    "role": "candidate",
    "profilePhoto": "",
    "resume": "",
    "skills": [],
    "bio": "",
    "_id": "64a4d6f8fc13ae2bb4501234",
    "createdAt": "2026-07-04T15:00:00.000Z",
    "updatedAt": "2026-07-04T15:00:00.000Z"
  }
}
```

### 🔑 Step 3: Login the User
Test the login route by sending the credentials:

```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "candidate@example.com", "password": "securepassword123"}'
```

**Expected Response (`200 OK`):**
```json
{
  "success": true,
  "message": "Login successful",
  "data": {
    "user": {
      "name": "Interview Candidate",
      "email": "candidate@example.com",
      "role": "candidate",
      "profilePhoto": "",
      "resume": "",
      "skills": [],
      "bio": "",
      "_id": "64a4d6f8fc13ae2bb4501234",
      "createdAt": "2026-07-04T15:00:00.000Z",
      "updatedAt": "2026-07-04T15:00:00.000Z"
    },
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
  }
}
```

### ❌ Step 4: Test Login with Incorrect Credentials
Verify that security validations fail cleanly:

```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "candidate@example.com", "password": "wrongpassword"}'
```

**Expected Response (`401 Unauthorized`):**
```json
{
  "success": false,
  "message": "Invalid email or password"
}
```

## 📬 Testing with Postman

Postman allows you to visually test API endpoints. Follow these detailed steps to verify the registration and login APIs.

### 1. Register a User in Postman
1. Open Postman and create a new request tab by clicking the **`+`** button.
2. Select **`POST`** from the HTTP method dropdown.
3. Enter the request URL: `http://localhost:5000/api/auth/register`
4. Click on the **Body** tab below the URL bar.
5. Select the **raw** radio button and choose **JSON** from the format dropdown.
6. Enter the following JSON payload:
   ```json
   {
     "name": "Interview Candidate",
     "email": "candidate@example.com",
     "password": "securepassword123",
     "role": "candidate"
   }
   ```
7. Click the **Send** button. You should receive a status code of **`201 Created`** with the registered user data.

---

### 2. Login the User in Postman
1. Create another request tab.
2. Select **`POST`** from the HTTP method dropdown.
3. Enter the request URL: `http://localhost:5000/api/auth/login`
4. Go to the **Body** tab, select **raw**, and set the format to **JSON**.
5. Input the registered email and password credentials:
   ```json
   {
     "email": "candidate@example.com",
     "password": "securepassword123"
   }
   ```
6. Click the **Send** button. 
7. You should receive a status code of **`200 OK`**. Under the `data` block, notice the `token` key. Copy this string value; it is the generated JWT token that subsequent authenticated requests will use.

---

### 3. Testing Login Failure
1. Under the same `/login` tab, modify the password to an incorrect one (e.g., `"wrongpassword"`).
2. Click the **Send** button.
3. You should receive a status code of **`401 Unauthorized`** and a JSON body containing `"message": "Invalid email or password"`.
